### Response to the four directions in VTT-20261012-005

1. Snapshot/outbox boundary: ACCEPT WITH REFINEMENT.
   - Register the subscription's live buffer before opening the REPEATABLE READ snapshot
     transaction, or use durable outbox replay after the snapshot. Registering after the
     high-water read leaves a race.
   - The canonical outbox high-water mark stays server-side. Exposing it to the client would
     reintroduce the hidden-activity side channel that opaque projection versions are intended
     to remove.
   - The client receives only `subscriptionId` and its projection-local sequence baseline. The
     server uses the internal outbox cursor to discard, project, and drain buffered events.

2. Opaque versions and sequencing: ACCEPT WITH REFINEMENT.
   - Entity tokens are opaque equality-only concurrency values.
   - Delivery sequence is dense and local to one `subscriptionId`, spanning durable scene,
     combat, and persistent-chat projection frames. It is not a canonical campaign sequence.
   - Redis may hold the live counter. Redis loss rotates `subscriptionId`, emits
     `vtt.resync_required`, and produces a fresh sanitized snapshot; PostgreSQL/outbox recovery
     remains authoritative.

3. Rejection enum and receipts: COUNTER THE ENUM; ACCEPT THE RECEIPT BOUNDARY.
   - Proposed v1 codes:
     `invalid-schema`, `unsupported-version`, `unknown-command`,
     `authentication-required`, `unauthorized`, `rate-limited`, `command-id-reused`, `stale`,
     `conflict`, `validation-failed`, `rule-violation`, `recipient-offline`,
     `resync-required`, `temporarily-unavailable`, and `server-error`.
   - Replace `invalid-target` with privacy-safe `validation-failed`; missing, hidden,
     wrong-campaign, and inaccessible targets must not be distinguishable. Field issues are
     allowlisted and are returned only after the referenced field/entity is already authorized
     for that principal.
   - Successful commands and deterministic post-capability, post-lock outcomes (`stale`,
     `conflict`, `validation-failed`, `rule-violation`) get durable receipts. Schema, version,
     unknown-command, authentication, authorization, and rate-limit failures do not create rows.
     A corrected retry uses a new command ID. Reuse with a different normalized digest returns
     `command-id-reused` from the existing receipt lookup and creates no second receipt.

4. PostgreSQL-authoritative table grants: ACCEPT.
   - Pairing codes are ephemeral and may live hashed in Redis; issued grant hashes, campaign
     binding, expiry, epoch, and revocation are authoritative in PostgreSQL.
   - Revocation commits the epoch bump and outbox event atomically. Redis fans it out and drops
     queued old-epoch frames. Subscribe and resync recheck PostgreSQL.
   - A 30-second PostgreSQL heartbeat ceiling is acceptable for alpha provided revocation
     fan-out is immediate and measured.

### Positions on D1-D9

- D1: ACCEPT WITH REFINEMENT. One integer `schemaVersion` is selected at subscribe and is also
  present on every inbound durable command and outbound durable frame. V1 does not silently
  downgrade. Unsupported versions enter the explicit version-mismatch/reload state.
- D2: ACCEPT WITH REFINEMENT. Identity is `(kind, id)`; the opaque version is data, not part of
  identity. Snapshots replace the complete subscription state atomically. Patches contain whole
  projected entity replacements plus explicit removals; omitted fields are never merged.
- D3: COUNTER THE ROLE VOCABULARY. Campaign roles are `gm`, `assistant`, `player`, and
  `observer`. `table` is a separate device principal and projection audience, not a campaign
  role. Its client capability list may be empty because it has no controls, while the server
  grant still authorizes subscribe-only access to the table projection. Global GM approval and
  campaign ownership remain separate properties.
- D4: ACCEPT WITH REFINEMENT. Use one dense durable-frame sequence per `subscriptionId`, not one
  global counter per audience. A duplicate is ignored, a noncontiguous value requires resync,
  and a mismatched subscription is discarded. Transients are revision-neutral.
- D5: COUNTER as described in direction 3.
- D6: DEFER implementation, but the walking skeleton still requires a dedicated table serializer
  over published state. A GM payload with controls removed is forbidden.
- D7: ACCEPT WITH REFINEMENT. Transients use a closed semantic type registry and a type-specific
  server policy. Entity transients require that entity in the recipient projection; coordinate
  pings/rulers require the published scene and allowed geometry. Authoring cursors and secret
  drag previews are not automatically relayed. The table is receive-only.
- D8: ACCEPT 8 Crockford-base32 characters and a 5-minute TTL for the skeleton. Generate codes
  with a CSPRNG, store only a hash/HMAC, make them single-use, and rate-limit by IP, code/challenge,
  and campaign rather than IP alone. The exchanged table credential remains high-entropy,
  PostgreSQL-backed, and independently revocable; it never contains GM credentials.
- D9: ACCEPT WITH REFINEMENT. One active scene per subscription. GM may request an authorized
  prep scene. A table cannot choose campaign or scene and follows only the server-owned published
  table pointer. A scene switch rotates `subscriptionId` and sends a complete sanitized snapshot;
  no canonical event is broadcast directly to a broad campaign room.
