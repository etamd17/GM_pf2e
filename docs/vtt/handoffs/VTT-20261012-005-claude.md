### The four directions

1. Snapshot/outbox boundary: ACCEPT, with this mechanism.
   - The snapshot is read in one REPEATABLE READ transaction that also reads the outbox high-water mark.
   - The snapshot carries that mark as its cursor.
   - From subscribe onward, the fan-out buffers that audience's events and releases only those after the cursor.
   - The client drops anything at or below the cursor.
   - Missed and duplicated commits are then impossible by construction, rather than merely unlikely.
2. Opaque versions instead of canonical counters: ACCEPT. Canonical counters are a side channel: a table seeing the scene version jump from 5 to 9 learns that hidden edits happened.
   - Gap detection: one monotonic sequence per audience stream, which counts only frames that audience received, so it leaks nothing. Patches carry `seq`, and the client detects a gap with `seq != last + 1`.
   - Expected versions in commands: opaque per-entity tokens, compared by equality only. The client never does arithmetic on them.
3. Rejection enum and durable receipts: proposed closed enum
   - `invalid-schema`, `unsupported-version`, `unknown-command`, `unauthorized`, `rate-limited`, `stale`, `conflict`, `invalid-target`, `rule-violation`, `server-error`.
   - Durable receipts only for rejections decided after capability checks and record locks: `stale`, `conflict`, `invalid-target`, `rule-violation`. A retry with the same commandId must then return the same answer.
   - No receipt for `invalid-schema`, `unsupported-version`, `unknown-command`, `unauthorized` or `rate-limited`. Otherwise an unauthorized client could write rows, and rate limiting would turn into durable state.
   - `unauthorized` carries no detail. It must not reveal whether the target exists.
   - A client that receives `stale` re-issues with a NEW commandId and fresh expected versions. That keeps receipts deterministic.
4. PostgreSQL is authoritative for table grants and revocation: ACCEPT.
   - Redis may cache a grant but never decides one.
   - Revocation commits a grant-epoch bump and an outbox event. The fan-out closes that table's sockets and drops queued frames for the old epoch.
   - Subscribe and resync recheck the grant in Postgres. A heartbeat recheck bounds the damage if the outbox is delayed. Proposed ceiling: 30 s.

### Positions on the D items (detail in the design doc, section 8)

- D1 Versioning: one integer protocol `schemaVersion`, declared at subscribe. Below the supported minimum, the server returns `unsupported-version`; the client enters its version-mismatch state, and the table reloads itself.
- D2 Patches: whole-entity replacement keyed by kind plus id, with the opaque version token and an explicit `removed` list. When an entity leaves a projection, that audience receives a `removed` entry. For the table, hidden and deleted must look identical, which is intended.
- D3 Roles: the fixed set is gm, assistant, player, observer and table. The snapshot carries the effective capability list so the client can show the right chrome; the server enforces capabilities regardless. The table's capability list is empty.
- D4 Sequencing: covered by direction 2. One sequence per audience stream spans scene, combat and chat frames.
- D5 Rejections: covered by direction 3.
- D7 Transients: they pass through the same audience filter as patches. A transient about entity X goes only to audiences whose current projection contains X. GM pings and rulers go to the table, matching the legacy scene_beacon. The table sends nothing.
- D8 Table pairing:
  - The GM issues a short code: 8 characters of Crockford base32 (about 40 bits), single use, 5-minute TTL, with attempts rate-limited per IP.
  - Redeeming the code yields a device grant scoped to campaign plus table audience. It never carries GM credentials, it is stored in Postgres, and it is revocable (see direction 4).
- D9 Subscription scope: one active scene per connection, scoped to the campaign. The table follows a server-owned "table scene" pointer and receives a scene-switch frame followed by a fresh snapshot. The GM may subscribe to any scene. That is enough for the skeleton and the walking slice.
