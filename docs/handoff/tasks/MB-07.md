# MB-07: turn on the Mistborn rules for a campaign

<!-- ============ BRIEF (written before work starts) ============ -->

- **Owner:** claude (heavy code: rules engine, saved character data). Codex reviews each
  milestone.
- **Branch:** `claude/mb-07-mistborn-rules` from `origin/main`.
- **User decision (2026-10-26):** wire the real Mistborn rules into the site. Until now a
  "Mistborn" campaign is the Mistborn look over the **Stormlight rules**. The reviewed Mistborn
  rules (MB-00 to MB-02) are installed, but nothing in the site turns them on.

## Where things stand

- The engine exists. `systems/cosmere/rules/profiles.py` picks a rules profile from the
  campaign's `rules_binding` (its exact package pins), and `mistborn_profile.py`,
  `mistborn_build.py`, `mistborn_runtime.py`, `mistborn_actions.py` and
  `mistborn_encounters.py` hold the Mistborn mechanics. `CosmereBuild` (`build.py`) is the
  facade over either engine.
- **Nothing sets a Mistborn `rules_binding`.** `/api/cosmere/world` changes only the look. MB-06
  hand-wrote a binding into test campaigns, and with it six pages crash (local inventory,
  2026-10-26):
  - `/cosmere/builder`, new, edit and level-up: `mistborn_profile.create_build` receives the
    facade object rather than a document;
  - `/cosmere/pc/<pid>`, `/cosmere/pcs`, `/cosmere/player`, `/cosmere/gm` and
    `/cosmere/gm/vitals`: Stormlight-only calls such as `build.order()`.
- The bestiary and tracker show Stormlight adversaries only.

## Rules for this work

- **Stormlight stays byte-identical.** Every change branches on the actor's rules world; the
  Stormlight path keeps its current code. Regression tests compare Stormlight output.
- **Systems never share mechanics.** No Stormlight concepts get stubbed into the Mistborn
  engine (no fake `order()` on `MistbornBuild`). The app branches instead.
- **Opening a page never rewrites a saved file.**
- **The private rules data stays out of git.** Tests that need it skip when it is absent, as the
  existing Mistborn tests do. CI therefore covers the Stormlight side and the plumbing, and the
  Mistborn pages are verified locally against the installed bundle. Each milestone reports
  both.

## Milestones

1. **The campaign rules switch.**
   - The GM chooses Stormlight rules, Mistborn Era 1 or Mistborn Era 2 for a Cosmere
     campaign. A Mistborn choice pins `cosmere.core` plus the newest installed
     `cosmere.mistborn.core` and era package from one release.
   - Allowed **only while the campaign has no Cosmere characters**, because a character's
     build carries the campaign's pins and must match them. Otherwise the request is refused
     with a plain message.
   - Mistborn rules force the Mistborn look.
   - Without the Mistborn data installed, the server refuses with "install the Mistborn rules
     data first".
   - Existing look-only Mistborn campaigns keep working unchanged.
2. **No crashes.** Every Cosmere page loads for Mistborn-rules characters in both eras, as GM
   and player:
   - the roster, player home, GM hub and Vitals show Mistborn facts (path, metalborn type,
     metals, Investiture) instead of Radiant ones;
   - the sheet shows Allomancy (Investiture, burnable metals, vials) and Feruchemy
     (metalminds and charges) from the build and its saved runtime state, and hides the Radiant,
     Ideals, Surges, Shardblade and Fabrial sections.
3. **The Mistborn builder:** name, ancestry, starting path, metalborn type and metals for the
   era, attributes, skills, talents, expertises, and level-up. It is validated live through the
   existing profile-neutral preview, and saves through the existing builder path.
4. **The bestiary and tracker:** the era's adversaries from the installed bundle, adding them
   to combat through `tracker_block`, and the Mistborn encounter budget.
5. **Sheet actions:** burn, tap and store through the existing Mistborn action API (CAS
   revisions and receipts), with live repaint.
6. **Verification and release:** a browser pass in both eras on desktop and phone, the
   Stormlight control, Codex's review, and a merge once CI is green. The user installs the
   1.1.2 bundle on Railway, then switches a fresh campaign to Mistborn rules.

## Report (Claude, 2026-10-27)

Milestones 1 to 5 are built on `claude/mb-07-mistborn-rules`. Milestone 6 (Codex's review, the merge
and the user's bundle install) is next.

### What changed

- **The rules switch (M1).**
  - `GET/POST /api/cosmere/rules` reads or chooses `stormlight`, `era-1` or `era-2`.
    `profiles.mistborn_campaign_binding(era)` pins `cosmere.core` plus the newest installed release
    that has both `cosmere.mistborn.core` and the era package.
  - Changing rules is refused (409, with the reasons) once the campaign has a character (including
    a pending one), a fight in progress, a staged encounter or narrative scenes.
  - Mistborn rules force the Mistborn look, and `/api/cosmere/world` refuses Stormlight under them.
  - Back to Stormlight removes `rules_binding` outright: a stored null is a fail-closed value. That
    needed a new `remove=` argument on `_save_campaign_config`, limited to optional keys.
  - The GM hub has a Rules control under World skin, with the reason shown when it is fixed.
  - A route-policy entry was added for the new endpoint.
- **No crashes (M2).**
  - `systems/cosmere/mistborn_display.py` holds pure, read-only projections: the metalborn summary,
    the card identity and the sheet's metallic-arts panel.
  - The roster, player home, status board, hub and Vitals use `_cosmere_card_identity`, which keeps
    the old Stormlight code and adds a Mistborn branch.
  - Mistborn sheets render through `_render_mistborn_pc_sheet` on the same template. The Radiant,
    Ideal, Surge, Shardblade, Fabrial and Workshop sections are empty or hidden. A Metallic Arts tab
    shows each metal or metalmind, its power state, burning or depleted status, vials and charges,
    read from `runtime_state` (falling back to the older `play_state`).
  - The Move/Senses/Lift row is hidden for Mistborn (the engine does not compute it). The
    Investiture orb is read-only there: it changes through burns, and Breathe Stormlight does not
    apply.
  - New `lore.FERUCHEMY_STORES` lists what each metalmind stores, so Feruchemy rows no longer show
    the Allomantic effect.
- **The builder (M3).** `cosmere_builder_mistborn.html` covers:
  - name, level, ancestry, culture and the starting (ordinary) path;
  - the metalborn type for the era: one metal for a Misting or Ferring, one of each for Twinborn,
    every era metal for a Mistborn or Feruchemist, and Era 1 atium fixed to unlocked;
  - attributes, skills, talents filtered by the character's paths and metals (or all), expertises
    and story fields;
  - a live summary from the existing profile-neutral preview, with budgets and problems, plus a GM
    override;
  - saving through the drafts workflow in account mode, or the direct POST otherwise. It sends
    `metal_access` derived from the powers, as the engine requires.
- **Bestiary and tracker (M4).**
  - `systems/cosmere/mistborn_adversaries.py` turns a catalog adversary and its action records into
    the actor document `CosmereActor` reads. It infers nothing: an attack described only in text
    stays an ability, not a strike with invented numbers.
  - Under Mistborn rules the bestiary, the tracker picker and the hub count list only the era's
    adversaries. `_cosmere_doc_by_id` resolves them, so the statblock, adding to combat and restore
    after a restart all work. GM-scope catalogs are cached per exact binding.
- **Sheet actions (M5).**
  - Each metal offers the catalog actions the Mistborn action API applies deterministically:
    Allomancy actions as `spend`, and Feruchemy `store-`/`tap-` actions as start, then stop.
  - They post with a fresh request id and the saved revision, then reload to show the server's
    result. Errors from the API are shown as they come.

### Findings and limits

- **Engine: a Feruchemy talent is accepted for a character with no Feruchemy** when its only
  prerequisite is a runtime condition (e.g. Heavyweight Blow, `currently_tapping_weight`). Talents
  in a `feruchemy.<metal>` or `allomancy.<metal>` tree probably need the matching power as an
  acquisition rule. I did not change the engine; proposed as its own task.
- **Engine: stopping a store or tap in the same turn is refused** ("A named action can normally be
  used only once per turn"), because the stop is treated as a second use of the named action.
  Whether stopping should be free is a rules question. The page shows the refusal.
- **Ordinary heroic-path talents (Agent, Envoy, and so on) are not in the Mistborn bundle**, so the
  builder offers only metalborn and metal talents. This is a data gap from MB-00, not a page bug.
- **CI cannot exercise the Mistborn pages**, because the private data is not in git. Those tests
  skip there and pass locally with the bundle.
- **The rules switch's "no characters" check runs outside the file lock.** Two simultaneous
  requests could slip past it. That is acceptable for one GM; noted rather than fixed.
- **Older look-only wording remains on the hub tiles** ("Stormlight Command & Tools", "Radiant
  order & surges"). That is MB-06's territory (Codex is fixing wording there).
- **The installed bundle on Railway is 1.1.0.** The switch works with any installed release that
  has both packages, but the reviewed content arrives with the 1.1.2 install.

### Review fix (Claude, 2026-10-28): Codex's changes-requested on 934635a2

- **The defect:** the builder's `collect()` built the payload from scratch. Saving through it erased
  `occupation`, `relationships`, `loyalties` and `personality` (and any other field the form does
  not edit), and reset `heroic_paths` to the starting path alone.
- **The fix:** `collect()` now calls `mergeCollected(BASE, edits)` (between `// MERGE START/END`).
  - It starts from the saved build and applies only the form's edits, so the four fields above
    survive, as do notes, inventory, currency, goal entitlements and epic choices.
  - It drops the server-derived fields (Allomancy/Feruchemy ranks, metal access, advancement grants,
    pins, theme) and rederives metal access from the powers.
  - It keeps acquired heroic paths other than the old starting path and the metalborn paths, which
    the engine re-adds from their keys.
  - A restored draft replaces `BASE` with the draft's own build. Server-owned validation is
    unchanged.
- **Tests, in `test_mistborn_pages.py`:**
  - Node runs the template's own merge code: unedited fields kept, derived fields dropped, an earned
    path kept, metal access rederived, and the base never mutated.
  - With the private data: the collector's output, built from the real page `BUILD`, goes through
    `_build_cosmere_document` (the drafts publication path) and through `POST /cosmere/builder`, and
    the reload keeps all four fields.
- **Results:**
  - `test_mistborn_pages.py`: 17 passed with the 1.1.2 bundle; 2 passed, 1 skipped for the
    collector tests without it.
  - `node --check` on the rendered builder script: clean.
  - All templates parse.

### Required: preserve unedited character fields in the Mistborn builder

`templates/cosmere_builder_mistborn.html:260-274` constructs a fresh build in
`collect()`, omitting occupation, relationships, loyalties and personality.
The existing save route normalizes those missing fields to empty strings.
Opening an existing character and saving therefore erases those fields even
when the user has not edited them. The collector also replaces heroic_paths
with only the selected starting path; preserve additional existing paths unless
an explicit, validated edit removes them.

Reproduction: extracted the actual `collect()` function and executed it under
Node with a saved Misting's form values, then submitted its output to the real
`POST /cosmere/builder` route. The route returned 200; reloading the saved PC
showed all four synthetic values (Courier, Sibling, Crew, Careful) replaced by
empty strings. Notes are correctly retained by the existing owner-private
field preservation and are not part of this finding.

Carry forward supported fields that the new UI does not edit, then overlay the
explicit form edits. Keep server-owned grant/entitlement validation intact.
Add a save-and-reload regression through the real collector and route; also
cover a character with more than one heroic path. Cover both direct save and
the draft submission boundary, which use the same collector.
