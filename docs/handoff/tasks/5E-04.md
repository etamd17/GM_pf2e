### What the queue said vs. what is true
The queue named "Draconic Ancestry, Totem animal, Favored Terrain". Two are already built:
Favored Terrain is `('Natural Explorer', 'Ranger', 'classic')` in `FEATURE_CHOICES`, and
Totem Spirit is an in-feature option block (`character.py` ~line 417). **Do not touch those.**
The real gap is species *versions*, and Draconic Ancestry is one case of it.

## Goal
24 species in the data carry `_versions`. The resolved export turns each one into a base
record plus one full record per version. Examples: 2014 Dragonborn -> "Dragonborn (Black)", ...;
2024 Elf lineages; 2024 Tiefling legacies; Gnome; Goliath giant ancestry; Aasimar MPMM; Kobold.
Today the builder lists the base and every version side by side. Picking the **base** silently
skips the sub-choice: no ancestry, so no breath-weapon type, and a resistance picked
independently of it. Make the sub-choice an explicit, required choice on the base species.

## Approach
1. **Bug to fix first.** `compute`'s sheet `resist` (~line 557) runs `_lower_list` over
   `race['resist']`, which can contain `{'choose': {...}}` dicts. The sheet then shows the raw
   text `{'choose': {'from': [...]}}` as a resistance (reproduce: base `dragonborn|phb`,
   classic, any class). Keep only string entries there; chosen resistances already come in
   through `ctx.grants.resist`. Do the same for `immune` on the next line.
2. **Find versions.** A version record has `_versionBase_isVersion: true` and
   `_versionBase_name` / `_versionBase_source` naming its base (check with
   `C.get('race', 'dragonborn (black)|phb')`). Add `content.race_versions(name, source) -> list`
   that returns the version records of a base. One indexed query or a cached scan of
   `all_records('race')` are both fine; cache it, and clear the cache in `content.reload()`.
3. **Engine.** When `build.race` is a base that has versions, add a required `Choice`
   `id='race:version'`, `kind='species_version'`, label `'<Species>: choose a version'` (for
   PHB/XPHB Dragonborn use `'Draconic Ancestry'`). Its options are
   `{'value': <version id>, 'label': ...}`. Name formats differ: 2014 uses
   `Dragonborn (Black)` (label `Black`), 2024 uses `Elf; Drow Lineage` (label `Drow Lineage`).
   Take the text after the last `; `, else inside the last `( )`. Checked: PHB Dragonborn has
   10 versions, XPHB Elf and Tiefling 3 each. When it is
   answered with a valid option, run the rest of `compute` on the **version** record instead of
   the base: the version is a complete record, including the right resistance and breath
   weapon text. Keep `build.race` as the base id, so the builder's species tab still
   highlights the base. A stale or invalid value is an error, exactly like other choices.
4. **Builder.** In `pSpecies`, hide records with `_versionBase_isVersion` from the grid. The
   summaries come from `routes._summaries('race')`; carry the flag through so the template can
   filter. The choice renders through the existing generic option list in `choiceHTML`,
   because options are `{value, label}` dicts. Check that it does, and add a small branch if
   it doesn't.
5. **Back-compat.** A saved character whose `build.race` is already a version id (picked from
   today's grid) must keep working, with no new pending choice. Version records have no
   `_versions` themselves, so step 3 doesn't fire for them; assert that in a test.
