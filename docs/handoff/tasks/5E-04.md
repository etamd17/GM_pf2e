### What the queue said vs. what is true
The queue named "Draconic Ancestry, Totem animal, Favored Terrain". Two are already built:
Favored Terrain is `('Natural Explorer', 'Ranger', 'classic')` in `FEATURE_CHOICES`, and
Totem Spirit is an in-feature option block (`character.py` ~line 417). **Do not touch those.**
The real gap is species *versions*, and Draconic Ancestry is one case of it.

## Goal
24 species in the data carry `_versions`. The resolved export turns each one into a base
record plus one full record per version. Examples: 2014 Dragonborn -> "Dragonborn (Black)", ...;
2024 Elf lineages; 2024 Tiefling legacies; Gnome; Goliath giant ancestry; Aasimar MPMM; Kobold.
Today the builder lists the base and every version side by side. Picking the **base** silently
skips the sub-choice: no ancestry, so no breath-weapon type, and a resistance picked
independently of it. Make the sub-choice an explicit, required choice on the base species.

## Approach
1. **Bug to fix first.** `compute`'s sheet `resist` (~line 557) runs `_lower_list` over
   `race['resist']`, which can contain `{'choose': {...}}` dicts. The sheet then shows the raw
   text `{'choose': {'from': [...]}}` as a resistance (reproduce: base `dragonborn|phb`,
   classic, any class). Keep only string entries there; chosen resistances already come in
   through `ctx.grants.resist`. Do the same for `immune` on the next line.
2. **Find versions.** A version record has `_versionBase_isVersion: true` and
   `_versionBase_name` / `_versionBase_source` naming its base (check with
   `C.get('race', 'dragonborn (black)|phb')`). Add `content.race_versions(name, source) -> list`
   that returns the version records of a base. One indexed query or a cached scan of
   `all_records('race')` are both fine; cache it, and clear the cache in `content.reload()`.
3. **Engine.** When `build.race` is a base that has versions, add a required `Choice`
   `id='race:version'`, `kind='species_version'`, label `'<Species>: choose a version'` (for
   PHB/XPHB Dragonborn use `'Draconic Ancestry'`). Its options are
   `{'value': <version id>, 'label': ...}`. Name formats differ: 2014 uses
   `Dragonborn (Black)` (label `Black`), 2024 uses `Elf; Drow Lineage` (label `Drow Lineage`).
   Take the text after the last `; `, else inside the last `( )`. Checked: PHB Dragonborn has
   10 versions, XPHB Elf and Tiefling 3 each. When it is
   answered with a valid option, run the rest of `compute` on the **version** record instead of
   the base: the version is a complete record, including the right resistance and breath
   weapon text. Keep `build.race` as the base id, so the builder's species tab still
   highlights the base. A stale or invalid value is an error, exactly like other choices.
4. **Builder.** In `pSpecies`, hide records with `_versionBase_isVersion` from the grid. The
   summaries come from `routes._summaries('race')`; carry the flag through so the template can
   filter. The choice renders through the existing generic option list in `choiceHTML`,
   because options are `{value, label}` dicts. Check that it does, and add a small branch if
   it doesn't.
5. **Back-compat.** A saved character whose `build.race` is already a version id (picked from
   today's grid) must keep working, with no new pending choice. Version records have no
   `_versions` themselves, so step 3 doesn't fire for them; assert that in a test.

## Report
- **Changed:** Added a cached `content.race_versions()` index, cleared it during content reload,
  and made a base species' resolved version an explicit `race:version` choice. A valid answer
  supplies the complete version record while the saved build keeps the base id; direct saved
  version ids still compute without a new choice and resolve through the same normalized cached
  record. PHB/XPHB Dragonborn uses the label "Draconic Ancestry"; the other versioned bases use
  their species name and readable version labels.
  Invalid version ids are normal choice-validation errors. Fixed the five FTD Chromatic records
  whose upstream resolved data leaves a generic resistance choice by recovering their fixed
  resistance from the base `_versions` metadata. Fixed multiple fixed resistances so they grant
  together instead of becoming an alternative choice. Sheet resistance and immunity lists now
  ignore structured choice objects instead of stringifying them.

  plus the one duplicate `Dragonborn (Base)|PHB` export scaffold, leaving the existing subrace and
  other non-version rows unchanged. PHB and XPHB each show one plain Dragonborn row. Changing the
  base species clears `race:version` in the same save patch so a prior version cannot block the
  change. The existing generic choice buttons render the `{value, label}` options without a new
  UI branch.

## Review

**Claude, 2026-10-14: accepted. No required fixes.**

Read the full working-tree diff (`content.py`, `routes.py`, `rules/character.py`, `rules/grants.py`,
`builder.html`, tests) against the brief, then checked it live on a local server on this tree
(real `dnd5e_data/`, throwaway data folder and 5e campaign). Did not rerun the test suite.

- **Species grid:** filtering "dragonborn" shows one PHB and one XPHB Dragonborn; no version rows
  and no `Dragonborn (Base)` scaffold. The FTD Chromatic/Gem/Metallic bases and the EGW subraces
  still show, as intended.
- **PHB Dragonborn (classic), clicked in the UI:** Choices tab shows one required "Draconic
  Ancestry" with 10 colors (Black ... White). Clicking Black: `resist == ['acid']`, no other
  `race:*` choice, nothing pending, sheet race "Dragonborn (Black)", Breath Weapon and Damage
  Resistance present, no `{'choose': ...}` text anywhere. The Species tab still highlights the
  base `dragonborn|phb`.
- **Switching species:** clicking Human afterwards saved `race = human|phb` with `race:version`
  removed in the same save; Human is highlighted; no errors.
- **XPHB Elf / Tiefling:** each gets "<Species>: choose a version" with three options (Drow / High
  Elf / Wood Elf Lineage; Abyssal / Chthonic / Infernal Legacy). Answered, the sheet uses the
  version record (e.g. "Elven Lineage (Drow)", Abyssal gives poison resistance). The remaining
  `race:*` choices are the species' own (Keen Senses skill, spellcasting ability, size).
- **Old saved ids:** `dragonborn (chromatic; black)|ftd` saved directly computes the same race,
  resistances (`acid`), features and choices as picking it through the base, minus
  `race:version`, with no new choice. `dragonborn (black)|phb` direct: acid, no choices, no
  errors. A leftover `race:resist` answer on an old character is ignored, not an error.
- **Invalid answer:** `race:version` set to an Elf lineage on Dragonborn is refused with 422
  "Draconic Ancestry: ... is not an option", and nothing is saved.
- **Code:** the FTD Chromatic resist recovery is narrow (only versions whose `_variables.resist`
  is a list of strings and whose resolved `resist` still holds a choose object). Both new caches
  clear in `content.reload()`. The builder's `save({race, choices})` matches `setChoice`'s
  whole-object replacement, so the deletion sticks.

Non-blocking notes:
1. Until a version is picked, the engine applies **no** species grants (Codex's deliberate choice,
   explained in `_select_race_version`). In the builder that's fine because the choice is required
   and shown. But a D&D Beyond import maps a Dragonborn or 2024 Elf/Tiefling to the base id, so
   an imported character shows no species bonuses, speed or senses from the species until the
   player picks the version. That fits the brief ("leave it pending on import") but is more
   visible than before; worth handling in the import follow-up.
2. The sheet summary shows the default 30 ft speed while the version is unpicked.
