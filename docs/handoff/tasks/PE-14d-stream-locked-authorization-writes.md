## Goal

Every SQL transaction that changes a campaign's GM, trashed status, membership, assignment, grants or tokens takes that campaign's stream row before the campaign row and before any state or authorization row, so command commits see authorization strictly at commit; grant issue/revoke become executor commands and token issue/scope/revoke become stream-locked writes. Visible behaviour of existing routes does not change.

## Decisions this brief fixes (reviewer: challenge these first)

1. **One global lock rule: stream row before campaign row.** Every writer calls `lock_stream(session, campaign_id)` (PE-14a) before the campaign row and before any state or authorization row, then locks the campaign row as today. Command transactions (PE-14b) take the stream row and read the campaign row without `FOR UPDATE` (PE-14c). This removes the stream/campaign deadlock cycle. No writer reaches several campaigns; `lock_stream` refuses a second campaign in one transaction (PE-14a).
   - **May precede the stream row:** only these, none of which a command transaction takes: the account-creation advisory lock 73420401 and SQLite `BEGIN IMMEDIATE` (identity.py:31-34); process locks taken outside the transaction (`_CAMPAIGN_STORE_LOCK`, workflow_store.py:27); and unlocked locator reads, such as the invitation locator read that names the campaign. No stream-holding transaction may take 73420401.
   - **Invitation order.** Every transaction that locks an existing invitation row uses one new helper, `services.lock_invitation_for_write(session, code) -> tuple[Campaign | None, Invitation | None]`, in `core/persistence/services.py`:
     1. Unlocked locator read `session.get(Invitation, code)`. If it is missing, return `(None, None)`. Copy `located_campaign_id` into a local (the later `populate_existing` re-read refreshes the same identity-map object, so comparing against `locator.campaign_id` would always match).
     2. On PostgreSQL, `SET LOCAL lock_timeout` (Decision 4), then `lock_stream(session, located_campaign_id)`.
     3. Campaign `SELECT ... FOR UPDATE` on `located_campaign_id`.
     4. Invitation `SELECT ... FOR UPDATE` with `populate_existing=True`.
     5. If the locked row is missing or its `campaign_id` differs from `located_campaign_id`, return `(campaign, None)`. The caller treats this as a missing invitation and raises before any write; there is no retry (no writer changes `Invitation.campaign_id` today, so this branch is defensive).
     6. Otherwise return `(campaign, invitation)`. The helper never checks `trashed_at` or any invitation field; callers revalidate as today: `creates_account` (identity.py:289), campaign trashed (services.py:112-113), and prior redemption, revoked, remaining uses, expiry and user (services.py:126-152).

     `identity._lock_invitation` delegates to the helper, which covers signup redemption, `revoke_invite` and `consume_invite`. In `TransactionalStore.redeem_invite`, the helper replaces only the locator read and its raise (services.py:104-106), the campaign `FOR UPDATE` (:107-111) and the invitation `FOR UPDATE` and its raise (:114-121). Its `(None, None)` and `(campaign, None)` results map to the existing `InviteUnavailableError("invite does not exist")`. The trashed check (:112-113, `InviteUnavailableError("campaign is unavailable")` when the campaign is None or trashed) is kept and runs right after the helper returns, before any other check or write. Resulting orders: signup is advisory lock (PG) or `BEGIN IMMEDIATE` (SQLite), locator, stream, campaign, invitation, user insert, then the second helper call inside `TransactionalStore.redeem_invite`, which re-enters the held stream, campaign and invitation; existing-user redemption is locator, stream, campaign, invitation. Neither path waits for an earlier lock while holding a later one. Same-campaign re-entry relies on PE-14a's `lock_stream` returning the held row without waiting (`test_lock_stream_reentry_same_campaign`); a second `SET LOCAL lock_timeout` is harmless. Invitation rows are not authorization inputs under C:460-465; revoke and consume take the stream only to keep one order. Known limitation, not handled: if a campaign row were hard-deleted between the locator read and `lock_stream`, the lazy stream insert raises an FK error that surfaces as `StoreUnavailable`, not "invite unavailable"; no SQL path hard-deletes campaigns today.
   - **Exception: `create_campaign`** inserts the campaign row and the creator's GM membership first, then calls `lock_stream` in the same transaction (the stream row's FK to campaigns makes an earlier call impossible). No other transaction can reference the uncommitted campaign, so nothing needs serializing. `campaign_import._import` follows the same pattern. Both are declared in the AST test's `EXEMPT` list.
2. **Wherever the write is a SQL transaction.** The rule attaches to the SQL transaction, whatever the campaign's authority: the contract makes the lock part of every authorization change (C:460), and in file authority it only serializes against nothing, at negligible cost. Today that is `sql` mode only; `json` and `shadow` write JSON and are unchanged.
3. **Process locks stay outside or before.** `workflow_store` keeps `_CAMPAIGN_STORE_LOCK` first, then the stream row, then the campaign row. No code path may take a process lock (`_CAMPAIGN_STORE_LOCK`, `_LIVE_CAMPAIGN_DISPATCH_LOCK` `app.py:535`, `ENCOUNTER_LOCK` `app.py:2312`, `campaign_lock` `core/obsidian_sync.py:52`, D&D store locks) while holding a stream row. Command transactions never take a process lock. The token revoke tombstone (PE-14c) takes and releases `campaign_lock` before the transaction opens, and the mint mirror and `repair_token_mirror` take it only with no transaction open, so `campaign_lock` is never held with a stream row.
4. **Lock timeout.** On PostgreSQL each writer issues `SET LOCAL lock_timeout` from PE-14b's `STREAM_LOCK_TIMEOUT_MS` (import it; never a second copy) immediately before `lock_stream`. In plain writers a timeout (55P03) surfaces through the existing database-error path (`StoreUnavailable`), so no route gains a new response; token mint and revoke surface it as PE-14c's `TokenStoreUnavailable`, which their routes already map to 503; grant commands get the executor's `503 temporarily_unavailable`. Import the constant inside the writer function, never at module top (a module-top import from `core/commands/executor.py` into `core/persistence/` makes an import cycle, because `core/persistence/__init__.py` imports `.services` and the executor imports `core.persistence` modules).
5. **Commands vs. plain writes.** Membership, assignment, GM and trash changes stay plain SQL writes that take the lock (they run in file authority too). Grant issue/revoke are executor commands, so they are db-only (C:794-797): `grant.issue_level_unlock`, `grant.issue_retrain`, `grant.set_quartermaster`, `grant.revoke`; GM, or a scoped token for the first two only (C:860, C:851). Each type declares `allowed_principals` (PE-14a `CommandType`): `grant.issue_level_unlock` and `grant.issue_retrain` take {USER, INTEGRATION_TOKEN}; `grant.set_quartermaster` and `grant.revoke` take {USER}, so a token is refused them at check 1 (PE-14a's `check_envelope`, called by PE-14b) whatever its scope. Membership, assignment, GM, trash and token writes are not command types and declare nothing. Subjects: for unlock/retrain, the character, keyed as `("character.build", character_id)` (PE-13a's revision kind; there is no plain `character` kind); the campaign for QM; for `grant.revoke`, the grant itself (kind `grant`, visibility per PE-14c), so a missing or hidden grant is `404` at check 5 and a revoked or consumed grant is terminal: `409 already_finalized` at check 6. For unlock/retrain, `lock_plan(ctx)` always locks the subject through `ctx.locks.character_states([(character_id, <build domain>), ...])` (the domain value PE-13a enters under `character.build`), whatever `expected` contains (so an intent command with empty `expected` still reaches check 5 with the subject key registered, and a character of another campaign registers `None` and answers `404`), (the dependency set below admits only the subject's own `character.build` row in `expected`); QM and revoke lock no character rows. Declared type fields (PE-14a `CommandType`; dependency sets and payload id fields per C:87-95):
     - `grant.issue_level_unlock`: subject kind `character.build`; dependency set `{character.build: the subject}`; payload id fields none (`target_level` is a value); `requires_expected=False`.
     - `grant.issue_retrain`: subject kind `character.build`; dependency set `{character.build: the subject}`; payload id fields none (`build_revision` is a value); `requires_expected=False`.
     - `grant.set_quartermaster`: subject kind `campaign`; dependency set empty; payload id fields none: `user_id` is a value, not a record id (there is no `user` record kind in PE-13a/13b), and the check-9 adapter refuses with `422 rule_violation` unless it names an active player member of this campaign, read in `ctx.session`; `requires_expected=False`.
     - `grant.revoke`: subject kind `grant`; dependency set empty; payload id fields none; `requires_expected=False`.

   Grant rows are not a `CommandLocks` step and are serialized by the stream row, which every grant write and every `consume` (PE-14c) holds. `lock_plan` registers the campaign (QM) or the grant (revoke) through `ctx.locks.register_serialized(kind, id, record)`, after `stream()` and within the `STREAM_SERIALIZED_KINDS` allowlist (`campaign`, `session`, `grant`; PE-13a), so it appears in `ctx.records`. `record` is a `StateRecord | None`: for `grant.revoke`, `lock_plan` reads the grant row by id within the campaign and registers `None` when there is no such grant (the `404` at check 5) or `StateRecord.serialized("grant", id, payload)` when it exists, never the raw ORM row; QM registers the campaign the same way. **Registration.** All four types register `derives_rules=False` (issuing or revoking a grant derives no rules, so they never fail `503 content_mismatch`, C:41-42) and a `rules_adapter`, which PE-14a's `register()` requires and from which PE-14b builds PE-13b's check runner. Its `check(ctx, override)` passes for three types (their refusals are authorization and check-1 refusals, not check 9); for `grant.set_quartermaster` it refuses `422 rule_violation` unless `user_id` names an active player member of this campaign. Its `build_edition_matches(subject_record, pin)`: for `grant.issue_level_unlock` and `grant.issue_retrain`, whose subject is a character, it applies the contract rule unchanged (C:48-50, profile to edition at C:35-39): for a D&D profile it returns True only when the character build's `edition` equals the pin profile's edition (`dnd5e-2014` is `classic`, `dnd5e-2024` is `one`), and for profiles with no build edition (`pf2e`) it returns True; so a grant for a character awaiting edition conversion is refused `422 edition_mismatch` like any other command on it. For `grant.set_quartermaster` and `grant.revoke` it returns True, since their subjects (campaign, grant) are not characters and check 8 never calls it. Token issue, scope change and revoke are plain stream-locked writes callable by the GM in any authority, since tokens predate db authority. Grant event names are registered here (C:1102): `grant.issued`, `grant.revoked`, emitted through `ctx.emit` (PE-14b).
6. **Tokens follow PE-14c's storage decision.** Option A (chosen by the user, 2026-11-14): in `sql` mode PE-14c's order is kept exactly (PE-14c Decision 1), and PE-14d adds only the `lock_timeout` statement and `lock_stream` at the start of each SQL write transaction, nothing outside it. Revoke: (0) a short read-only SQL read of the row, closed before step 1 (no stream lock; it writes nothing); (1) with no transaction open, take `campaign_lock`, stamp the file record's `revoked_at` (or append a revoked record built from the step-0 row), write the file and release the lock; (2) only if step 0 or 1 found the id, open the SQL write transaction, which here starts with the `lock_timeout` statement and `lock_stream`, then sets `revoked_at` where it is NULL (or inserts the row already revoked when only the file had it), and commits. Mint: the SQL write transaction (here starting with the `lock_timeout` statement and `lock_stream`) commits first; after commit, with no transaction open, it takes `campaign_lock` and appends the file record, insert-if-absent. So `campaign_lock` is never held while a stream row is held. The import transaction in `verify_token` and the partial-revoke completion in `repair_token_mirror` (both PE-14c) are writers too and take the stream the same way. Recovery from a failed or partial write follows PE-14c Decision 1; the rollback gate is the exporter in PE-14g, not the mirror, and this task never claims the mirror alone protects a rollback. `json` and `shadow` keep `tokens.json` as bearer authority, unchanged and unlocked. `scope` and `replaces_credential_id` exist only on the SQL record; the `scope` parameter added here makes PE-14g's rule reachable: a token whose scope is not exactly `["@live"]` is exported as revoked. The mirror and its repair run only in `core/obsidian_sync.py`, `core/persistence/integration_tokens.py` and the route layer, never from `core/commands` (PE-14b's subprocess `sys.modules` guard forbids `core.obsidian_sync` there). If the user picks Option B, the SQL shadow record write takes the stream row the same way, after the file write and outside `campaign_lock`. Record which option was implemented.
7. **Subscription closure** stays post-commit and unchanged in this task; PE-31b owns closing streams "before any further frame" once events flow (C:628-630). Record this.
