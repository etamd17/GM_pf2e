## Decisions this brief fixes (reviewer: challenge these first)

1. **Token storage (user chose Option A, 2026-11-14).** The contract needs the token record and scope re-read inside the stream-locked transaction (C:435) and a committed, permanent revocation readable in the status read (C:275). A file cannot join that transaction. Options:
   - **A (chosen): SQL is the token store in SQL mode.** New `integration_tokens` table. Only with `runtime.sql_enabled()` (`OWNERSHIP_BACKEND=sql`) do `create_token`/`verify_token`/`revoke_token`/`list_tokens` use SQL; `json` and `shadow` keep `tokens.json` as the bearer authority, unchanged. Those modes have no SQL token rows, so a token command there is refused at check 4; that is acceptable because db authority implies SQL mode.
     - **Import.** The lazy import of `tokens.json` runs on the bearer path (`verify_token`, called from `services/obsidian_sync.py:524-528`) and from `repair_token_mirror` (below), always before any stream-locked transaction: take `campaign_lock`, read the file, release it; then, only if the file lists an `id` that SQL lacks or a `revoked_at` that a live SQL row lacks, open its own SQL transaction (PE-14d later adds the `lock_timeout` statement and `lock_stream`), insert missing rows (`id` kept as `credential_id`, scope `["@live"]`, C:851-852; `minted_by_user_id` NULL) with insert-if-absent, and copy a file revocation onto a live row, then commit. The import transaction is one function in `core/persistence/integration_tokens.py` that both callers use. `authorizer.load` never imports: a missing token row means not authorized.
     - **Strict file read in SQL mode.** `_load_tokens` (`core/obsidian_sync.py:63-69`) reads through `storage.load_json(path, {})`, which turns `OSError` and invalid JSON into `{}`, and it also turns a non-object document into `{}`. In SQL mode that would read a corrupt file as "no records": a partly revoked token would pass, and a tombstone or repair would rewrite the file from an empty list. So SQL mode uses a new strict loader `_load_tokens_strict(campaign_id)` in `core/obsidian_sync.py`: a missing file counts as an empty document; an `OSError`, invalid JSON, a non-object document or a `tokens` value that is not a list raises `TokenStoreUnavailable`. `verify_token`, the import, the revoke tombstone, the mint file append and `repair_token_mirror` all read through it, so none of them writes over a file it could not parse. `json` and `shadow` modes keep `_load_tokens` unchanged.
     - **Campaign filter.** `credential_id` is a global key, so every SQL token read and write in the import, revoke (steps 0 and 2) and `repair_token_mirror` selects and updates only rows `WHERE campaign_id = :campaign_id`. A `token_id` that exists in SQL only for another campaign counts as not found: if the file of this campaign has no record for it either, revoke writes nothing to either store and returns `False` (route 404). An import that finds a file id already held in SQL by another campaign skips it and logs `obsidian_token_import_conflict campaign=<id>` with no secret; it never inserts or changes the other campaign's row.
     - **`last_used_at` in SQL mode.** `verify_token` updates SQL `last_used_at`, at most once every 300 s per token, in its own short transaction after the authentication decision: a single `UPDATE ... WHERE credential_id = :id AND campaign_id = :campaign_id`, with no `lock_stream` and no `lock_timeout` statement, because `last_used_at` is not an authorization input (C:460-465). It writes nothing to the file in SQL mode (the file's `last_used_at` write at `core/obsidian_sync.py:124-135` stays for `json` and `shadow` only). A failure of this update is logged and does not fail the request. PE-14d lists this update in its AST inventory's EXEMPT list with the reason "not an authorization input (C:460-465)".
     - **Bearer check in SQL mode, and import failure.** `verify_token` decides from the file read it already made (under `campaign_lock`, before the import), not from the import's outcome: if a file record whose `token_hash` matches the bearer digest has `revoked_at`, it returns `None` (401), whether the import later commits, fails or is skipped. If the import transaction raises (including PE-14d's lock timeout while a long command holds the stream), `verify_token` logs `obsidian_token_import_failed campaign=<id>` with no secret and continues to the SQL check. That fall-through cannot accept a token the file has revoked, because the file check above already refused it; it accepts only a token that is live in SQL and not revoked in the file (a SQL-minted token whose file append has not landed has no file record, and every revoke writes a revoked file record before SQL). If the strict file read fails, `verify_token` raises `TokenStoreUnavailable`; `token_required` (unchanged, catches only `ValueError`, `services/obsidian_sync.py:523-526`) lets it through and the app's `/api` error handler (`app.py:8571`) answers 500. It never treats an unreadable file as "not revoked".
     - **Revoke is write-ahead.** In SQL mode `revoke_token(campaign_id, token_id)` runs: (0) read the SQL row for `token_id` in this campaign (campaign filter above) in a short read-only transaction and close it; (1) take `campaign_lock` with no transaction open and read the file strictly; if the file has a record for the id, stamp its `revoked_at`; if it has none but step 0 found a SQL row, append a file record built from that row (`id`, `label`, `token_hash` from `token_digest`, `last_four`, `created_at`, `last_used_at`) with `revoked_at` already set; write the file and release the lock; (2) only if step 0 or step 1 found the id, open a SQL transaction (PE-14d later adds the `lock_timeout` statement and `lock_stream`), set `revoked_at` where it is NULL, or, when SQL has no row but the file had one, insert the row already revoked (scope `["@live"]`, `minted_by_user_id` NULL), and commit. If neither store had the id at steps 0-1, nothing is written and the result is `False`. This closes the race with a concurrent mint: once mint's SQL row is committed, a revoke always leaves a revoked file record, so mint's later insert-if-absent file append finds the id and does nothing; and a revoke that saw the id in neither store never revokes a row that commits after it. A failure in any step raises a new `TokenStoreUnavailable` (defined in `core/obsidian_sync.py`), which the revoke route maps to `503 token store unavailable`. A failed file write changes nothing. A failure after the file stamp leaves the file refusing the token (the bearer check above refuses it even if the import that would complete SQL fails), and the SQL side is completed by the next bearer request whose import commits, or the next GM token-page visit (repair); the revocation is never reversed. The return value is `True` when either store has the id at steps 0-1, even if it is already revoked (retry-safe), and `False` (route 404) only when neither does. The two writes are not atomic (C:458); they are ordered so every partial state fails closed.
     - **Mint and file-copy repair.** `create_token` commits the SQL row first. A SQL failure raises `TokenStoreUnavailable` (route 503), writes nothing to the file and returns no token. After the commit, outside any transaction, it takes `campaign_lock` and appends the file record, insert-if-absent by `id`. If that file write fails, the route still returns 201 with the token (SQL is authoritative) and logs `obsidian_token_mirror_failed campaign=<id>` with no secret. `list_tokens` in SQL mode (the GM page, never the bearer path) runs `repair_token_mirror(campaign_id)` in `core/persistence/integration_tokens.py`: it reads the SQL rows outside any transaction; under `campaign_lock` it copies missing records and missing revocations from SQL to the file, insert-if-absent, writing only when something differs, never clearing a revocation and never deleting a record; after releasing the lock it completes partial revokes (a file `revoked_at` that a live SQL row lacks) through the import transaction. A repair failure is logged and the list is still served from SQL, plus file rows not yet imported (read-only; none when the strict read failed), so the GM page can see and revoke a token that has never authenticated.
     - **Invariant.** Revocation only moves one way. SQL `revoked_at` is never cleared, and no mode switch bypasses it: every revoke that writes SQL has first left a revoked file record (stamped, or inserted from the SQL row when mint's file append has not landed yet), and mint's append never overwrites an existing record, so even an unsupported direct flip to `json` still refuses a revoked token, including after a crash at any point in the revoke (before the file write nothing is revoked; after it the file refuses). This rests on three facts at `791936f1`: every `tokens.json` write is `storage.atomic_write_json` (`core/storage.py:248-262`, temp file then `os.replace`); every write is a read-modify-write under `campaign_lock`, which is a process lock; and the app runs one worker process (`Procfile:1`, `railway.toml:6`, `--workers 1`). With more than one process, or a hand edit or restore of `tokens.json`, a concurrent write could drop a revoke's file stamp, so the claim does not hold there. The flip is unsupported in any case; the guarantee for the supported rollback is PE-14g's export gate.
     - **Not the rollback guarantee.** The file copy alone does not protect a rollback to JSON. After a direct flip, a SQL-minted token whose file record never landed is refused (401); the runbook already makes a direct flip unsupported. The rollback gate is PE-14g, which builds each campaign's `tokens.json` from SQL in the supported rollback export and must merge before production uses SQL token storage. This task never claims otherwise.
     - One source of truth per mode; the bearer path changes in SQL mode only.
   - **B (not chosen; kept for the record): SQL shadow record.** `tokens.json` stays the bearer authority in every mode; SQL holds `credential_id`, scope, `replaces_credential_id` and `revoked_at`, written after the file. Smaller change to the Obsidian path, but a token can be revoked in one store and live in the other (C:458: a file write paired with a SQL write is never atomic), and every db-authority check would need both stores. The same write-ahead order (file first, then the SQL record) would still be needed, and every SQL-side revocation check (C:275, PE-14f) would also have to read the file. Under B, PE-14g is dropped: the file stays authoritative, so no token export is needed.
   The user chose A on 2026-11-14, so the file list and acceptance are A's.

3. **Token scope** is a JSON list of command `type` names fixed at mint, plus the symbolic entry `"@live"` meaning "the current live-command set" (C:852), so tokens that exist today get `["@live"]`. A token may send `override` for a type only when its scope holds the entry `"override:<type>"` and the registered `CommandType` for that type does not set `override_gm_only` (Decision 6); `"@live"` never implies override (a judgment on how "a token scoped for it", C:137, is spelled; record it in the report).    - **Session types.** The C matrix (C:854-876) has no session row, so `campaign_role_allows` carries an explicit rule for `session.start` and `session.end` (C:481, C:489 "same principals"): allowed for the GM, including the site admin (C:847), and for an integration token of this campaign whose scope permits the type, either by naming it or through `"@live"`; refused for every other role, the QM included. The contract does not say whether `"@live"` ("the current live-command set", C:852) covers the session types; this brief decides that it includes both (a judgment), so existing plugin tokens can still start and end sessions. Override on `session.end` stays GM or site admin only (Decision 6).
   - **Authorizer attributes a visibility resolver may read.** Read-only public attributes set by `load`: `is_gm` (true for the campaign's GM and the site admin, from SQL rows only), `is_site_admin`, `principal_kind` (USER or INTEGRATION_TOKEN, from the authenticated principal), `user_id` (None for a token), `token_campaign_id` (the token row's `campaign_id`; None for a user) and `campaign_id`. Resolvers use only these and the public methods; they never read private fields. A `session` record is visible to any principal that passed check 4 for a session type, so PE-14e's resolver, registered with `register_visibility("session", ...)`, returns true for the GM or site admin (`is_gm`) and for a token whose `token_campaign_id` equals `campaign_id`.
4. **Replacement.** `replaces_credential_id` is honoured only when both tokens belong to the same campaign and the replacement was minted by a principal who was that campaign's GM at mint (`minted_by_user_id` recorded) (C:268-270, C:328-331).
5. **Visibility for check 5.** The authorizer resolves visibility per record kind from the projection table (C:635-645) and the union of roles (C:647-648) for kinds that exist now: `campaign`, `character.build`, `character.play`, `encounter`, `combatant`, `clock`, and `grant` (visible to the GM, the grant character's owner and editor, and the QM user for their own QM grant; no other principal, tokens included). 6. **Override (check 4).** `override_allowed(type)` takes the principal kind from the authenticated principal passed to `load` (never from the envelope) and GM and admin status from the SQL user and campaign rows only. It is true for the GM and the site admin (C:847). For a token it is true only when the scope holds `"override:<type>"` and PE-14a's registered `CommandType` for `type` has `override_gm_only` False; a type the registry does not know gives False, so the check fails closed.
