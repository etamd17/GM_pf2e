## Goal
GM art uploaded for a tracker combatant is left on disk when the picture is replaced,
the combatant is removed, or the encounter is cleared. Delete those files, without ever
deleting one still in use.

## Approach
- Add `images.collect_garbage(cid, keep: set[str]) -> int` that deletes every file in
  `images_dir(cid)` matching `NAME_RE` whose name is not in `keep`, skipping files
  modified in the last 10 minutes (an upload whose row isn't saved yet).
- `keep` = every `portrait` in `store.list_pcs(cid)` plus every combatant `image` in
  `store.load_encounter(cid)` plus every `image` in saved plans if plans ever gain one
  (they don't today -- leave a comment).
- Call it after `'clear'` and `'remove'` in `routes.api_gm_combat`, and after a
  replace in `api_gm_combat_image`. Wrap in try/except OSError: GC must never fail a
  request.

## Acceptance
- [x] Replacing, removing, or clearing deletes the orphaned file; a PC portrait and an
      image still on another combatant survive.
- [x] A file younger than 10 minutes is never deleted.
- [x] New tests in `tests/test_dnd5e_images.py`; `pytest -q tests/test_dnd5e_images.py
      tests/test_dnd5e_app_integration.py` passes.
- [x] HANDOFF.md: remove the "combatant art is not deleted" bullet.

## Out of scope / do not touch
- PC portrait deletion (already correct), the 5etools art under `static/dnd5e_img/`.

**Claude, 2026-10-13: deletion safety accepted; one small change requested before commit.**

Checked and safe:
- **References:** keep set = every PC `portrait` + every combatant `image`, read under
  `encounter_lock`, after the action, so a just-removed combatant's image is correctly absent and
  a shared image survives while any combatant still uses it. Plans have no images (comment left).
- **Fail closed on unreadable characters:** `list_pcs` drops corrupt files and files whose inner
  `id` differs from the filename; the filename-vs-loaded-id comparison catches both and skips
  collection. Correct direction (unknown references never count as unused).
- **Grace period:** `mtime > now - 600` is skipped, so new uploads (written via tmp + replace
  before the row is saved) and future-dated files are safe.
- **Only managed files:** `NAME_RE.fullmatch` (32 hex + `.webp`), `is_file(follow_symlinks=False)`,
  symlinked directory refused, `.tmp` and other names ignored, no recursion, per-campaign directory.
- **Concurrency:** single gevent worker; `encounter_lock` is an `RLock` and nothing else takes
  PC -> encounter, so no deadlock; a file removed by someone else (`FileNotFoundError`) is skipped.
- **Never fails a request:** caller catches `OSError` and logs.

Finding 1 (requested fix, low severity, not a safety issue):
- **One undeletable file stops the whole cleanup.** Reproduced: four old orphans, `os.remove`
  raising `PermissionError` for the first one scanned -> `collect_garbage` raised, **4 of 4 left on
  disk**. On Windows a file being served (`send_file`) is locked, and a file with bad permissions
  would block cleanup forever. Fix: inside the loop, `except OSError: continue` (keep the
  `FileNotFoundError` case), and optionally count skipped files for the log. Add a test that
  makes one file fail and asserts the other old orphans are deleted.
