## Goal

Create the per-campaign stream, receipt and event tables and the pure pieces every command needs before it runs: the envelope parser, the digest, the command-type registry with check 1, and plain stream reads for PE-31. No command executes yet.

## Decisions this brief fixes (reviewer: challenge these first)

1. **The stream row.** `campaign_streams(campaign_id PK, FK campaigns ON DELETE CASCADE, last_seq BIGINT NOT NULL DEFAULT 0 CHECK >= 0)`. It is lock-order step 1 (C:156-157). `streams.lock_stream(session, campaign_id)` locks it and conforms to PE-13a's `LockStream = Callable[[Session, str], Any]`; PE-14b passes it explicitly as `CommandLocks(session, campaign_id, lock_stream=streams.lock_stream)`, and PE-14d/e/f call it directly. There is no default binding and this task does not edit `command_locks.py`. Every writer takes the stream row before the campaign row and before any state or authorization row (PE-14d enforces this for the existing writers). `stream_epoch` stays on `campaign_state_authority` (C:29) and is not copied. The row is created lazily under the lock: `INSERT ... ON CONFLICT DO NOTHING`, then `SELECT ... FOR UPDATE`, so this task changes no campaign creator. Within one transaction: a second call for the same campaign returns the held row without waiting or re-inserting (PE-14d's invitation helper relies on this); a call for a different campaign raises, because no writer reaches several campaigns. The guard state lives in `session.info`, never in a module global, and is keyed to the current transaction: it stores the locked campaign, the row and the identity of `session.get_transaction()`, and an entry whose transaction is not the current one counts as not held. So the guard never survives `commit()` or `rollback()`: a Session reused for a new transaction (as `identity._transaction` and `Database.session()` allow) issues `SELECT ... FOR UPDATE` again and may lock any campaign. Because of the FK, the lazy insert works only once the campaign row exists in the transaction; `create_campaign` therefore inserts its campaign row first and then calls `lock_stream` (PE-14d's declared exception). A migration backfill is unnecessary and not done.
2. **Seq.** `allocate(stream, n)` returns `last_seq+1 .. last_seq+n` and stores the new `last_seq`, under the held lock (C:28, C:426). PE-14b's `ctx.emit(EventDraft) -> (event_id, seq)` calls it at emit time, so a seq is known while `apply` runs; the receipt's seq range comes from the emitted events. Gaps are impossible because allocation and insert share the transaction.
3. **No FK on receipts and events.** `game_events` has no FK (C:1088); `command_receipts` also has none, matching `CharacterWorkflowReceipt` (`models.py:455-477`); both are kept for the campaign's life across epochs (C:244-245). Names stay distinct from `character_workflow_receipts` and `audit_events`.
4. **Receipt columns:** `campaign_id`, `principal_kind` (`user` | `integration_token`), `principal_id`, `operation_id`, `digest`, `status` (`committed` | `rejected`), `applied_status`, `code`, `revisions` JSON, `event_ids` JSON, `seq_first`/`seq_last` (nullable for refusals), `stream_epoch`, `created_at`; unique `(campaign_id, principal_kind, principal_id, operation_id)` (C:242-244). No response body (C:244).
   - `applied_status` is `committed` or `pending` on a committed receipt and NULL on a rejected one (CHECK). A replay answers HTTP 202 when it is `pending` and 200 otherwise, so the "recorded status" of C:354-355 survives; the status read (PE-14f) reports `state: committed` for both. This column is a judgment (C:243 lists only `committed`/`rejected`); record it in the report.
   - `code` is NULL on a committed receipt and NOT NULL on a rejected one (CHECK).
   - `digest` is 64 lowercase hex, nullable, with a CHECK that `digest IS NULL` if and only if `code = 'abandoned'`: an abandon receipt (`status = rejected`, `code = abandoned`, C:299-302) has no envelope to hash.
   - Lookup order is PE-14b's, recorded here so the columns support it: `code = abandoned` → `409 abandoned`; else same digest → replay; else `409 operation_id_reused` (C:357-360, C:373-375).
5. **Event columns** follow C:396-407 one-for-one: scalar columns for `event_id` (PK, 32 hex), `campaign_id`, `seq`, `stream_epoch`, `type`, `occurred_at`, `session_id`, `encounter_id`, `operation_id`, `action_id`, `causation_event_id`, `origin`, `principal_kind`, `principal_id`, `rules_profile`; JSON for `actor`, `subjects`, `changes`, `dice`, `explain`, `visibility`. Unique `(campaign_id, seq)`; index `(campaign_id, stream_epoch, seq)` for PE-31's cursor (C:582, C:588).
6. **Registry.** A `CommandType` declares `type`, subject kind, dependency set (`expected` kinds and each one's relation to the subject), payload id fields, `requires_expected`, `derives_rules` (only these types can fail `503 content_mismatch` at check 8, C:41-42), `allowed_principals`, `override_gm_only`, terminal predicate (C:87-95, C:130-135) and `lock_plan(ctx)`, the callable PE-14b calls after the receipt check to take lock-order steps 2-5. It also stores `apply(ctx)`, the callable PE-14b runs to make the change, and `rules_adapter`, an object with `check(ctx, override)` and `build_edition_matches(subject_record, pin)` from which PE-14b builds PE-13b's check runner. This task only stores `lock_plan`, `apply` and `rules_adapter`; it never calls them. `rules_adapter` is required for every type: `register()` raises `ValueError` when it is None, because PE-13b's runner fails at construction without an adapter and PE-14b always builds the runner from it. A type with no check-9 rule supplies an adapter whose `check` passes and whose `build_edition_matches` returns the edition answer its owner states.
   - `register()` raises `ValueError` when the type name is already registered; it never replaces an entry. Tests register test-only types under names unique to the test, so the module-level registry needs no unregister helper.
   - Every type owner (PE-14d, PE-14e, PE-30 and later) must state, per type: the subject kind (C:88-91); the dependency set, i.e. the `expected` kinds it may list and each one's relation to the subject (C:91-94; empty if none); the payload id fields with the record kind each names (C:94-95); `requires_expected` (C:130-135); `allowed_principals`; `override_gm_only`; `derives_rules`; and the `rules_adapter`. A type whose owner does not state all eight cannot register.
   - `allowed_principals: frozenset[PrincipalKind]` is a non-empty subset of {USER, INTEGRATION_TOKEN}; `register()` raises `ValueError` otherwise. It is a kind filter only: role, token scope, revocation and `override` stay at check 4 (PE-13b with PE-14c). A type whose subject or effect is membership, ownership, tokens or a QM grant declares {USER} (C:849-851). The types are registered by their owners: PE-14d (`grant.issue_level_unlock` and `grant.issue_retrain` {USER, INTEGRATION_TOKEN}; `grant.set_quartermaster` and `grant.revoke` {USER}) and PE-14e (`session.start` and `session.end` {USER, INTEGRATION_TOKEN}).
   - `override_gm_only: bool = False`, set at `register()` time. When True, only the GM or the site admin may send `override` for the type; a token is refused even if scoped `override:<type>`. PE-14c's `override_allowed(type)` reads it from the registered `CommandType`, and an unregistered type gives False for a token, so the check fails closed. An override accepted at check 4 can then be read by the type's check-9 adapter and by its `apply` (as `session.end`'s `apply` runs `cancel_all`, PE-14e). Every registered type has both, so every type has an override path, and the field needs no validation of its own beyond being a bool. PE-14e registers `session.end` with it set; PE-30 sets it for encounter close.
7. **Check 1 is a standalone function that takes the authenticated principal.** In `registry.py`: `check_envelope(envelope: Mapping, principal: Principal, *, route_campaign_id: str) -> CheckedEnvelope`. `envelope` is the raw request mapping. It is pure, runs before any transaction and touches no database. `principal` must be a verified `core.request_context.Principal` passed by the caller; anything else raises `TypeError` (PE-14b answers it as 500). Identity is never read from `envelope`: keys such as `principal`, `principal_id` or `user_id` in the body are ignored like any other unknown key. Fixed order; the first failure raises `EnvelopeRefusal(code)` (attributes `code`, `http_status`; Approach 4) and nothing is written:
   1. `principal.kind` not in {USER, INTEGRATION_TOKEN}: `403 not_permitted` (C:233-235). This covers LEGACY_GM, LEGACY_PLAYER, PUBLISH_TOKEN and ANONYMOUS; ANONYMOUS is not named in C:235, so refusing it is a judgment; record it in the report.
   2. An INTEGRATION_TOKEN whose `principal.campaign_id != route_campaign_id`: `403 not_permitted`.
   3. Static envelope checks, each `400 bad_envelope` (C:97-100, C:356): unknown `schema` or `type`, malformed `operation_id` (C:27), body `campaign_id` different from the route's, an `expected` kind outside the dependency set (C:99), or a missing required `expected`. The last is a judgment (a static-schema failure under check 1, C:99-100; C:356 does not list it); record it in the report. Then compute the digest; a NaN is `400 bad_envelope`. Unknown keys are ignored (they are outside the digest, C:236-241, and never read).
   4. `principal.kind not in command_type.allowed_principals`: `403 not_permitted`. It runs after step 3 because it needs the type, and reveals nothing because the registry is static.

   The result is a frozen dataclass `CheckedEnvelope(envelope, command_type, principal, principal_kind, principal_id, digest)`, where `envelope` is the parsed envelope and `principal_kind`/`principal_id` come from `principal_key(principal)`. PE-14b takes the receipt key, the event principal fields, `ctx.principal` and the digest only from it. Revocation is invisible to check 1 (no database); a revoked token is refused at check 4. PE-14b calls `check_envelope`; PE-13b's runner covers checks 4-9 only and does not call it. This task depends on neither.
8. **Stream reads for PE-31.** `stream_watermark(session, campaign_id) -> int` is a plain read of `last_seq` (0 when there is no row), taking no lock. `events_after(session, campaign_id, after_seq, limit) -> list[EventRow]` returns events ordered by seq. Both are raw reads; projection and the 200-per-page limit (C:588-590) belong to PE-31.
9. **Greenlet contention** (C:826-828) is proved here, on the stream lock itself, because it is a property of the lock primitive. If the test shows psycopg blocks the gevent hub, stop and report before PE-14b: the fix is a design change. (PE-14b sets `lock_timeout` from its `STREAM_LOCK_TIMEOUT_MS` constant; this task sets none.)

1. Models and migration per decisions 1, 4 and 5, including the receipt CHECKs. Follow 0003's conventions. Populated downgrade (C:831-837): refuse while any `command_receipts` or `game_events` row exists, or any campaign's authority is `db`, `migrating` or `exporting`; refuse offline. Empty `campaign_streams` rows may be dropped (they hold only a counter; with no events, `last_seq` carries nothing). Upgrade then downgrade then upgrade round trip on SQLite and PostgreSQL.
2. Update the head pins listed in Context so the existing suites still test 0003 and 0004's own guards.
3. `streams.py`: `lock_stream(session, campaign_id) -> StreamRow`, `allocate(stream, n) -> range`, `stream_watermark(session, campaign_id) -> int`, `events_after(session, campaign_id, after_seq, limit) -> list[EventRow]`. `lock_stream` conforms to PE-13a's `LockStream` and requires an active transaction. Per Decision 1, it records the locked campaign, the row and the current transaction's identity in `session.info`; an entry from an earlier transaction is ignored. Within one transaction, a second call for the same campaign in the same transaction returns the held row without waiting or re-inserting; a call for a different campaign raises.
4. `envelope.py`: the principal-free body parser for C:226-231: require integer `epoch`, validate `operation_id` (C:27), and parse `override` as optional (C:137). It also defines `EnvelopeRefusal(code)`: the constructor takes the code only, and the attribute `http_status` is looked up from a fixed two-entry table (`bad_envelope` 400, `not_permitted` 403); any other code raises `ValueError`. PE-14b answers it by the attributes `code` and `http_status`. `envelope.py` also defines `principal_key(principal) -> tuple[str, str]`: USER gives `("user", user_id)`, INTEGRATION_TOKEN gives `("integration_token", credential_id)`, any other kind raises `EnvelopeRefusal("not_permitted")`. The first element is `PrincipalKind.value`, matching the receipt's `principal_kind` column. Whether the principal may send `override` is check 4 (PE-13b with PE-14c's `override_allowed`), not this task.
5. `digest.py`: SHA-256 of canonical JSON over `schema, campaign_id, type, subject, expected, rules, override, payload`; sorted keys, separators `(",", ":")`, `ensure_ascii=False`, `allow_nan=False`, integral floats as ints, absent `override` as `null` (C:236-241). Golden vectors: at least six, generated by running `00b334b4`'s `_canonical` on the same inputs where the key sets overlap, checked in as literals.
6. `registry.py`: `CommandType` (including `allowed_principals` and `override_gm_only`), `register(CommandType)` with the validation of Decision 6 (including the duplicate-name `ValueError`), `get(type)`, `CheckedEnvelope`, and `check_envelope(envelope, principal, *, route_campaign_id)` implementing check 1 in the fixed order of Decision 7. Register test-only types from the tests, never in product code. Real types register at import of their module, so `registry.py` also holds `COMMAND_MODULES: tuple[str, ...] = ()` (dotted module names, empty here) and `load_command_modules()`, which imports each listed module once (idempotent; an import error propagates). `check_envelope` calls `load_command_modules()` first, so an unregistered real type can never reach check 1 as 'unknown'. Each type-owning task (PE-14d, PE-14e, later adapters) appends its module to the tuple; nothing else in `registry.py` changes for them. Test: `test_load_command_modules_imports_listed_modules_once` (a listed throwaway test module registers once across two calls).
